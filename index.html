How it fires

Triggered when the original note lands in the database. One light LLM call against the note returns a categorised JSON. Medication entries fan out to MIMS in parallel so popovers are warm by the time the clinician hovers.

Step 1 Note generated Original note populated in DB.
Step 2 Extraction call Light LLM. Output-only.
Step 3 JSON returned Categorised entities. Generic names for meds.
Step 4 - parallel MIMS fan-out One API call per generic medication. Cached per session.
Step 5 UI ready Hover popovers + interactions check live in the note.

What the LLM returns

Flat JSON, no offsets, no IDs. The TipTap extension finds raw_span in the rendered note via string match and decorates it.

Scope

In scope (POC)

  • Output-only entity extraction with one light LLM call.
  • Six categories captured. Medications wired to UI.
  • Eager parallel MIMS fetch for medication TLDRs.
  • Popover anchored to the highlighted span.
  • "Check interactions" action in every medication popover.
  • String-matching via TipTap extension. No offsets, no IDs.

Out of scope (for now)

  • Country routing. MIMS only.
  • Vector DB lookup. Long-term direction, not POC.
  • UI affordances for diagnoses, investigations, symptoms, signs, plans.
  • Personalised guideline matching against patient context.
  • Re-running on note edits. Fires once per generation.

What "Check interactions" actually does

No bespoke interactions endpoint. The button composes a single evidence query and posts it to the existing evidence layer - the same path any other evidence question travels.

please outline all of the interactions, the drug interactions between
the following drugs,
  - metformin
  - lisinopril
  - atorvastatin

List items come from output_entities filtered to category == "medication". Default to the normalised term; falling back to raw_span is fine if we want to pass through exactly what the clinician wrote. Either way it's just a string + a list - no new infra.

Dependency - MIMS in evidence (EVI-1318)

Aryen is currently looking into the MIMS integration. The plan is to load MIMS content into Mongo (or a vector DB) so it's queryable from our own evidence layer - a near-perfect fit for this POC.

  • Medication TLDR and the interactions check can both pull from the same evidence source once MIMS content lives in our DB.
  • This work is potentially dependent on EVI-1318 landing - no need to duplicate the MIMS plumbing.
  • Comment added on EVI-1318 flagging the overlap.
  • Later we can expand beyond medications to the other entity categories the extractor already returns.

Heidi Verify Architecture

How the verification pipeline works under the hood: a two-step LLM call powered by Opus 4.5, followed by a programmatic summary calculation. Outputs feed the Issues tab and All Entities tab in the Scribe UI.

What it looks like in the Scribe UI

Note on the left with inline highlights for flagged content. Issues drawer on the right grouped by priority, with source-quote traceability and one-click magic-fix.

End-to-end pipeline

Two trigger modes: manual (clinician clicks "Verify") and auto (Verify runs automatically once the note is generated). Either way the analysis is asynchronous - typically under a minute. The clinician can navigate away and come back when notified.

Input Note generation prompt transcript + patient context + template + voice + clinician profile
→
Step 1 - LLM Entity extraction Opus 4.5
→
Step 2 - LLM Entity verification Opus 4.5
Step 3 - programmatic Summary calculation no LLM. counts derived from raw arrays
→
Output eval_result row + UI render Issues tab, All Entities tab, source tracing, magic fix
Auto mode - critical-path optimisation When Verify is set to auto, Step 1 (entity extraction) fires in parallel with the original note generation, since both consume the same source material (transcript + patient context + template). Step 2 (verification) only fires once the note has finished generating, because it needs the final note as input. Net effect: by the time the note appears, the extracted entities are already done; only the verification round-trip and the programmatic summary sit on the critical path before the UI lights up.
1Step 1 - Entity Extraction

Extract clinical entities from the inputs

A single LLM call (Opus 4.5) reads the full note generation prompt and pulls out everything clinically relevant. This establishes the ground truth of what the note should contain. Errs on the side of higher relevance when uncertain.

Inputs fed into the prompt

{transcript}Raw consultation transcript
{patient_details}Demographics, history
{patient_context}Clinician-supplied context
{notes}Contextual notes
{default_structure}Note template
{default_voice}Style preferences
{requirements}Note-gen requirements
{language}Session language
{country}Clinician country
{date_today}Date in clinician's format

2Step 2 - Entity Verification

Verify each entity against the generated note

A second LLM call (Opus 4.5) takes the extracted entities and the generated clinical note, then for each entity decides: is it present, is it accurately represented, and is there content in the note that wasn't in the source material?

Inputs fed into the prompt

{extracted_clinical_entities}Full JSON output from Step 1
{clinical_note}The AI-generated clinical note text

For each entity from Step 1: was it carried into the note? Is the representation accurate? Drives the All Entities tab.

Content found in the note that wasn't in any source material. Classified as a hallucination or a supported inference. Drives the Issues tab.

Aggregate counts in one object. Coverage = entities_present / total_entities_checked. Hallucinations bucketed by severity, missing entities bucketed by relevance. These are the numbers behind the "Issues 3 / All 17" indicators in the UI.

3Step 3 - Programmatic summary

Calculate summary metrics from the raw arrays

No LLM. The verification LLM's own summary counts are deliberately ignored. Every aggregate metric is calculated by iterating over the two arrays from Step 2, so the numbers always reconcile with the detailed data and the eval pipeline matches production.

Output - 13 fields written to eval_result

FieldDescription

Metrics - precision and recall

From the 13 fields above, two clinical quality dimensions are derived per record and averaged across the dataset:

Precision (by hallucination severity)

"How trustworthy is the note?" present / (present + hallucinations at that severity). Penalises false positives.

Recall (by entity relevance)

"How complete is the note?" present / (present + missing at that relevance). Penalises false negatives.

Why the architecture looks like this

Design choices

  • Two-step pipeline so extraction and verification can evolve independently and use different prompts.
  • Opus 4.5 on both steps - chose accuracy and depth over latency.
  • LLM-reported summary counts deliberately ignored. All aggregates are programmatic.
  • Exact quotes captured in both directions for source tracing in the UI.
  • Suggested fixes generated at verification time so magic-fix is one click.

Trade-offs

  • Latency typically under a minute. Async by design - clinician can navigate away.
  • Verifies note against transcript only. Transcript errors are not caught.
  • Estimated 1-2% false negative rate.
  • Quality bound by transcript quality.
